            Hybrid Cryptography
          
          

            왜 HTTPS는 '비대칭키'와 '대칭키'를 모두 사용할까요?
          

          

            HTTPS는 두 가지 암호화 방식의 장점만을 결합한 하이브리드 암호화(Hybrid Encryption) 방식을 사용합니다. 아래 카드를 클릭해 각 단계가 해결하는 보안 문제를 확인해 보세요.
          

        


        
        

          
          
          

            

              

                1
                신원 인증 (Authentication)
              

              
CA 디지털 인증서 검증

              

                해커가 가짜 서버를 만들어 공개키를 보낼 수 있습니다. 이를 막기 위해 공인 인증기관(CA)이 자신의 개인키로 서명한 SSL/TLS 인증서를 서버에 발급합니다.
              

            

            

              
🔍 브라우저의 검증 방법

              
브라우저에 미리 내장된 CA의 공개키로 인증서 서명을 복호화하여 진짜 서버인지 100% 확인합니다.

            

          


          
          

            

              

                2
                안전한 키 배송 (Key Exchange)
              

              
비대칭키(공개키/개인키) 활용

              

                비대칭키는 보안이 뛰어나지만 연산 속도가 느려 대용량 웹 데이터 전송에는 부적합합니다. 따라서 초기 대칭키(세션키)를 안전하게 공유할 때만 사용합니다.
              

            

            

              
🔑 공개키 잠금 → 개인키 해제

              
클라이언트가 서버의 공개키로 키 재료를 암호화해 보내면, 오직 서버의 개인키로만 풀 수 있습니다.

            

          


          
          

            

              

                3
                고속 데이터 암호화 (AES)
              

              
대칭키(세션키) 기반 HTTP 통신

              

                핸드셰이크가 끝나면 클라이언트와 서버 모두 동일한 대칭키(Session Key)를 갖게 됩니다. 이후 모든 HTTP 요청과 응답은 이 대칭키로 초고속 암호화됩니다.
              

            

            

              
⚡ 속도 + 보안 + 무결성 동시 달성

              
AES-GCM 같은 현대 암호화 알고리즘은 암호화와 동시에 데이터가 중간에 변조되지 않았는지(MAC) 검증합니다.

              OSI 7-Layer Architecture
              ·
              L7 (HTTP) + L6/L5 (TLS/SSL)
            

            

              HTTPS는 OSI 7계층의 어디에 있고, 어떻게 보안을 수행할까요?
            

            

              순수 HTTP는 최상위 7계층(응용 계층) 프로토콜입니다. 여기에 보안을 더한 HTTPS는 전송 계층(4계층 TCP)과 응용 계층(7계층 HTTP) 사이에 TLS/SSL 프로토콜(주로 6계층 표현 계층 · 5계층 세션 계층 역할)을 끼워 넣어 7계층 데이터 전체를 암호화합니다.
            

          


          
          

            

              L7 응용 계층
              HTTP (메시지)
            

            

              L6·L5 표현/세션
              🔒 TLS/SSL
            

            

              L4 전송 계층
              TCP (Port 443)
            

            

              L3 네트워크(IP) → L2 링크 → L1 물리

              🔒 L5~L7 보안 구간
            

            

              
            

          


          

            💡 실무 관점 참고: 현대 TCP/IP 4계층 모델에서는 L5·L6·L7을 하나의 응용 계층(Application Layer)으로 통합해 부르며, TLS를 4.5계층(전송 계층 위 보안 계층)으로 설명하기도 합니다.

              🔍 무엇이 보이고 무엇이 숨겨지나요?

              패킷 배달을 위해 L3 IP 주소, L4 포트(443), 그리고 초기 핸드셰이크의 도메인 이름(SNI)은 외부에서 볼 수 있습니다. 하지만 L6 표현 계층의 TLS 암호화 덕분에 도메인 뒤의 상세 URL 경로(예: /account/transfer), 쿼리 파라미터, 쿠키, 인증 토큰, POST 본문은 100% 암호화되어 제3자가 절대 볼 수 없습니다.
            

          


        


      


    


    
    
    
    


      
      

        

          

            L4 Transport Layer
            ·
            IANA Port Number System (0 ~ 65,535)
          

          

            Well-Known 포트란 무엇이며, 왜 HTTP는 80번·HTTPS는 443번일까요?
          

          

            IP 주소가 서버 컴퓨터를 찾아가는 '건물 주소'라면, 포트 번호(Port Number)는 그 건물 안에서 어떤 프로그램(웹 서버, 메일 서버, DB 등)에게 데이터를 전달할지 구분하는 '출입문(호실) 번호'입니다. 전 세계 표준 프로토콜들이 혼선 없이 통신하도록 국제인터넷주소관리기구(IANA)가 미리 약속해 둔 0번 ~ 1023번 번호대를 Well-Known 포트(잘 알려진 포트)라고 부릅니다.
          

        


        
        

          

            

              0 ~ 1023
              핵심 표준 구간
            

            
Well-Known Ports (잘 알려진 포트)

            

              IANA가 주요 표준 프로토콜용으로 예약한 번호입니다. 웹 브라우저가 URL에 포트 번호를 생략해도 http://는 80, https://는 443으로 자동 접속합니다. (리눅스/유닉스에서는 관리자 권한 필요)
            

          


          

            

              1024 ~ 49151
              애플리케이션 구간
            

            
Registered Ports (등록된 포트)

            

              특정 소프트웨어나 데이터베이스, 개발용 서버가 사용하는 포트입니다. 예: MySQL(3306), PostgreSQL(5432), 대체 HTTPS(8443), 웹 개발 서버(3000, 8080).
            

          


          

            

              49152 ~ 65535
              클라이언트 발신용
            

            
Dynamic / Ephemeral Ports (동적 포트)

            

              내 PC의 브라우저가 서버(443번)에 요청을 보낼 때, 응답을 되돌려받기 위해 운영체제(OS)가 임시로 자동 할당하는 발신자 포트입니다. 통신이 끝나면 반납됩니다.

              L4 Transport Layer
              ·
              신뢰성(TCP) vs 초저지연(UDP)
            

            

              전송 계층(L4)의 두 주역: TCP와 UDP는 어떻게 다를까요?
            

            

              응용 계층(HTTP/HTTPS)의 데이터를 목적지 포트까지 배달하는 방식에는 두 가지 표준이 있습니다. TCP는 전화 통화처럼 연결을 먼저 맺고 데이터 누락과 순서를 100% 보장하며, UDP는 엽서 보내기처럼 연결 절차 없이 데이터를 즉시 쏘아 보내 속도와 실시간성을 극대화합니다.

                구분 기준
                TCP (신뢰성 중심)
                UDP (속도 · 실시간성 중심)
              

            
            
              

                연결 방식
                연결 지향형 (3-Way Handshake로 연결 후 통신)
                비연결형 (연결 절차 없이 목적지로 바로 패킷 전송)
              

              

                데이터 신뢰성
                ✅ 높음 (ACK 확인 및 유실 시 자동 재전송)
                ⚠️ 낮음 (패킷이 중간에 유실되어도 재전송하지 않음)
              

              

                전송 순서 보장
                Sequence 번호를 이용해 보낸 순서대로 재조립 보장
                경로에 따라 도착 순서가 바뀔 수 있음
              

              

                흐름 / 혼잡 제어
                수신자 버퍼와 네트워크 혼잡도에 맞춰 전송 속도 자동 조절
                제어 기능 없음 (일정한 속도로 계속 전송)
              

              

                전송 속도 & 헤더
                상대적으로 느림 (헤더 20~60 Bytes)
                매우 빠름 (헤더 8 Bytes 고정)
              

              

                주요 활용 분야
                HTTP/1.1·2, HTTPS, 파일 전송(SFTP), 이메일(SMTP), 금융 거래
                실시간 스트리밍, 온라인 FPS 게임, 음성/영상 통화(WebRTC), DNS, HTTP/3(QUIC)
              

            
          

        

      


    


    
    
    
    


      
      

        

          

            

              3-Tier Web Architecture
              ·
              Web Server (DMZ) + WAS (Internal) + DB
            

            

              왜 실무에서는 웹 서버(Nginx, WebtoB, IIS)와 WAS를 분리할까요?
            

            

              웹 서버(Web Server)는 HTML, CSS, 이미지 같은 정적 리소스를 빠르게 응답하고 앞단에서 HTTPS(TLS) 암호화 해제(SSL Termination) 및 부하 분산을 담당합니다. 반면 WAS(Web Application Server)는 로그인·결제·DB 조회 같은 동적 비즈니스 로직 처리에 집중하여 서버 자원과 보안을 최적화합니다.
            

          


          
          

            

              🔒 SSL Termination (SSL 오프로딩)
            

            

              외부 구간은 웹 서버(:443)가 HTTPS 인증서와 암·복호화를 전담하고, 방화벽 안쪽(내부망)의 WAS와는 가벼운 내부 HTTP/전용 프로토콜로 통신해 WAS의 CPU 부하를 줄입니다.
            

          

        

      


      
      

        

          

            
🔀 요청 유형별 서버 계층 처리 흐름 시뮬레이터

            
요청 종류와 웹 서버 소프트웨어 스택을 선택해 패킷이 DMZ 웹 서버와 내부망 WAS를 어떻게 거치는지 확인해 보세요.

          


          
          

            
            
            
          

        


        
        

          실무 서버 조합 선택:
          
          
          
        


        
        

          
        

      


      
      

        
        
        

          

            

              Web Server / Proxy
              Open Source
            

            
Nginx (엔진엑스)

            

              비동기 이벤트 기반(Event-Driven) 구조를 채택해 적은 메모리로도 수만 개의 동시 접속을 처리하는 현대 웹 아키텍처의 표준 웹 서버입니다.
            

          

          

            
✨ 핵심 강점 & 주 조합

            
• 리버스 프록시, L7 로드밸런싱, HTTPS SSL Termination 최적화
• 주로 Tomcat(Spring Boot), Node.js, Gunicorn 앞단에 배치

          

        


        
        

          

            

              Enterprise Web Server
              TmaxSoft (국산)
            

            
WebtoB (웹투비)

            

              티맥스소프트가 개발한 상용 웹 서버로, 국내 은행·증권·공공기관의 미션 크리티컬 시스템에서 압도적인 점유율을 보유하고 있습니다.
            

          

          

            
✨ 핵심 강점 & 주 조합

            
• 국산 WAS인 JEUS(제우스)와 전용 소켓 프로토콜(WBAPI)로 초고속 연동
• 웹 서버와 WAS 간 장애 격리 및 대규모 트랜잭션 안정성 우수

          

        


        
        

          

            

              Windows Web Server
              Microsoft
            

            
IIS (Internet Information Services)

            

              Microsoft Windows Server에 기본 탑재되는 전용 웹 서버로, GUI 관리 콘솔과 Windows 보안·인증 체계가 완벽하게 통합되어 있습니다.
            

          

          

            
✨ 핵심 강점 & 주 조합

            
• ASP.NET / .NET Core(Kestrel) 애플리케이션 호스팅 및 리버스 프록시
• Active Directory(AD) 연동 사내 인트라넷 및 인증서 관리 용이

          

        


      


      
      

        

          
🏛️ 웹 서버(Web Server) vs WAS(Web Application Server) 역할 비교

        

        

          

            
              

                비교 항목
                웹 서버 (Web Server)
                WAS (Web Application Server)
              

            
            
              

                주요 처리 대상
                정적 콘텐츠 (HTML, CSS, JS, 이미지, 동영상 등 이미 완성된 파일)
                동적 콘텐츠 (사용자별 맞춤 데이터, 결제·로그인 로직, DB 연산 결과)
              

              

                대표 소프트웨어
                Nginx, WebtoB, IIS, Apache HTTP Server
                Tomcat, JEUS, JBoss(WildFly), WebLogic, Kestrel
              

              

                네트워크 배치 위치
                외부와 접하는 DMZ(완충 지대)에 배치 (80 / 443 포트 오픈)
                방화벽 안쪽 내부 보안망(Private Zone)에 배치 (DB 보호)
              

              

                HTTPS 보안 역할
                SSL/TLS 인증서 탑재 및 암·복호화 전담 (SSL Termination)
                복호화된 요청을 전달받아 세션·권한 검증 및 트랜잭션 수행
              

              

                분리 운영의 이점
                정적 파일 캐싱·압축으로 빠른 응답 및 리버스 프록시 라우팅
                장애 발생 시 웹 서버에서 점검 페이지 노출 가능, 무중단 배포(Scale-out) 용이
